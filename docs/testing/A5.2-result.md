## 2. 实施中发现并修复的缺陷

1. **resume 误用 `--session-id`**（对照设计 §4/§5.2）：初版 CLI 恢复路径复用 `NewHostWithReservedSessionID`，会把已有 ID 通过 `--session-id` 传给 Claude，而不是 `--resume`，等于以“新建指定 ID”语义启动已存在会话。已拆分为 `NewHostForResume` → `WithResume`，并以 `sessionSDKOptions` 集中保证两种模式的 SDK 选项互斥（新增 `TestSessionSDKOptionsSeparateNewAndResume`、`TestHostResumeReservesExistingID`、`TestHostResumeRejectsNewIDFromClaude`、`TestBuildRuntimeReservesSessionIDBeforeConnect`）。
2. **首轮前配对 CLI 测试存在数据竞争**：`TestRunWithRemoteActivatesBeforeFirstInput` 用普通 `bytes.Buffer` 同时被 run goroutine 写、测试读，`go test -race` 报 DATA RACE。已改为互斥保护的 `syncBuffer` + `waitForOutput`，并把“`session_started` 不重复 Activate”的断言改为等到 `session: <id>` 输出后再校验，避免早读误判。
3. **【人工验收发现，阻断 A5.2 主目标】首轮前扫码连接必失败，必须先在 PC 完成一轮会话后重连才成功**：
   - 现象（用户实机）：启动后把 `pairing:` 复制进 Web 页面 → 连接失败；PC 终端先完成一次会话后，Web 端重连才成功。
   - 根因：三端共用契约在浏览器端被单方面收紧。首轮前 Session 尚无任何 Turn，Go 侧 `TurnSnapshot.Source` 为零值，wire 上是 `"source":""`；而 `apps/mobile/src/protocol/decode.ts` 的 `decodeTurnSnapshot` 用 `requireNonEmptyEnum` 校验 `source`，解码抛 `field source has unknown value` → `client.ts` 判定 `protocolError` 并终止连接。PC 完成一轮后 `turn.source` 变为 `terminal`，解码通过，故“先会话再重连”能成功。
   - 修复：`decode.ts` 改用 `requireEnum` 允许空串，并补语义校验（`requestId` 非空时 `source` 不得为空——服务端 `applyNextInput` 对两者同时赋值）；`types.ts` 将 `TurnSnapshot.source` 放宽为 `InputSource | ''`；`reducer.ts` 的 `applySnapshot` 增加空 `source` 守卫（首轮前不创建任何消息）。
   - 门禁盲区与补测：原 `TestWebSocketPreTurnSubscribeReceivesStartingSnapshot` 只断言 snapshot 的**键集**、未断言 `turn.source` 的**值**；前端既有 fixture 使用了不真实组合 `{requestId:'', source:'mobile'}`，恰好掩盖缺陷；`cmd/channel-test-client` 不走前端解码器。现补三层测试：`internal/transport/server_test.go` 的 `TestWebSocketPreTurnSnapshotTurnWireShape`（固化首轮前 Turn 的精确 wire JSON）、`decode.test.ts` 两个用例（空 `source` 可解码 / `requestId` 非空但 `source` 空必须拒绝）、`client.test.ts` 的「首轮前 snapshot 仍能进入已连接（不报协议错误）」。
