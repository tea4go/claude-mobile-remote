### 长按复制：原生能力审查

- 当前 iOS 的剪贴板写入已通过 `src/native/clipboard.ts` → `SessionExperience.copyText` → `UIPasteboard.general.string`；长按计时、DOM Range 全选和菜单布局来自 `SelectableMessage.tsx`。系统选择手柄和高亮由 WebKit 提供，项目未接入原生触觉反馈，也未使用自建原生长按识别器或原生文本选择控件。
- [Capacitor 官方 Haptics API](https://capacitorjs.com/docs/apis/haptics) 支持从前端独立调用原生触觉反馈。因而钉钉长按时震动能说明有触觉反馈，但不能据此确认其消息渲染、选区和菜单的具体实现；未获得钉钉内部实现证据。
- [Apple 长按手势说明](https://developer.apple.com/documentation/uikit/handling-long-press-gestures) 将达到时长后的 `.began` 与抬手后的 `.ended` 分开。上一轮在抬手后全选是本项目的交互实现选择，不是 Capacitor 限制，本轮已改为长按阈值触发。
- [Apple UITextInteraction](https://developer.apple.com/documentation/uikit/uitextinteraction) 为符合 UITextInput 的自定义文本视图提供选择交互；[UIEditMenuInteraction](https://developer.apple.com/documentation/uikit/uieditmenuinteraction) 提供编辑菜单。触觉反馈、菜单和可调整的文本选区是不同能力，单独增加震动或原生菜单不能自动解决 DOM 选区冲突。
- 本轮直接核对安装的 React DOM：其被动监听处理涉及 touchstart/touchmove/wheel，不包括 touchend，不能把此前所有异常归因于 touchend 为被动事件。当前直接监听显式控制相关触摸事件，避免对 React 代理事件的默认配置作推断；iOS 原生选择识别与 DOM 选区是否仍有冲突，尚须真机证据。
- 审查结论：本轮先完成已确认的交互和布局修正，不能据此宣称已达到钉钉体验。后续若增加触觉反馈，应在首次长按成功建立选区时触发一次轻反馈；若转为完整原生文本选择，需要独立评估 Markdown、表格/代码、流式更新、滚动及三端等价交互。本轮未擅自新增插件或替换渲染架构。

### 长按复制：统一选区实现与待验收

- 用户反馈确认前一轮原生轻震通过；选区反复切换、系统菜单混入仍未通过。用户确认 D119，由组件统一管理高亮、开始/结束手柄和复制菜单，保留原消息卡片与 Markdown 展示。
- 消息正文及其后代持续局部禁用系统选择与呼出菜单，独立 Range 仅用于度量文字几何，不调用 Selection.addRange，也不使用系统 selectionchange 维护应用状态。触摸菜单只拦截，不能在 touchcancel 后再次全选；桌面明确右键与键盘菜单仍可进入选择。
- 长按达到约 500ms 时全选并轻震一次；松手不重选。组件绘制高亮和两个手柄，按 Unicode 字素边界调整并复制当前文本；代码/表格保留换行与单元格分隔。用户蓝色气泡使用浅色高亮，避免蓝色选区难以辨认。

- 外部点击、输入框聚焦、窗口失焦、后台、详情退出或流式内容变化时清除选区、高亮和菜单。复制失败保留当前选区供重试，连续点击去重，异步旧结果不覆盖后续选区。
