# A5.1 终端输入实时同步分阶段设计

- 日期：2026-08-25
- 子阶段：A5.1 终端输入实时同步（里程碑 A）
- 状态：用户已确认
- 依据：用户确认的实时同步范围、A5 设计 §6、D19、D27、D32

## 1. 目标

A5.1 让已连接的手机页面实时显示 PC 终端在连接建立后提交的纯文本输入，并继续按同一 `requestId` 展示对应 Claude 回复。该能力补齐双端文本会话的可观察性，完成后再进入 A6 VPN 真机联调。

A5.1 不把手机变成历史管理器：首次订阅、刷新或显式重连仍只取得现有 snapshot；扫码前或上一连接中的 PC 输入正文不恢复、不 replay、不持久化。

## 2. 范围

### 2.1 A5.1 实现

- A3 在 `turn_started` 领域事件的既有 `text` 字段中携带该 Turn 的规范化输入正文；
- A4 原样编码事件，并调整有界输出容量，使最大合法输入对应的事件可以完整发送；
- A5.1 将 PC 输入显示为独立输入消息，再按 `requestId` 累积 Claude 回复；
- 任意手机输入都统一进入 Session Controller FIFO，不区分设备身份；发送方在 `command_result` 后显示“已接收”，所有订阅端在 `turn_started` 时按 `requestId` 归并且不重复正文；
- 自动化覆盖 A3、A4、协议 decoder、reducer、组件与 App 闭环；
- 人工验证 PC 输入、手机输入、连续多轮和刷新边界。

### 2.2 A5.1 不实现

- snapshot 增加输入正文；
- 刷新、重连或新设备连接后恢复旧输入；
- 多轮历史、event replay、浏览器存储或服务端 transcript；
- Markdown、Thinking、Tool、审批、取消和复杂消息渲染；
- VPN 真机、Capacitor 或 HarmonyOS 工程代码。

## 3. 方案选择

采用复用既有 `DomainEvent.text` 的方案。`turn_started` 目前已经包含 `text` 字段，只是 A3 发布时留空；A5.1 为该字段补充输入正文语义，不新增 event kind，不改变 envelope 结构，也不提升协议版本。

未采用新增 `input_received` 事件：它会增加事件枚举、seq 流和三端分支，却不能提供超出 `turn_started.text` 的必要信息。未采用 Web 专用消息：它会污染三端共用契约并破坏 A3 为唯一状态来源的分层。

## 4. 共用契约语义

### 4.1 `turn_started.text`

版本 1 事件保持现有 JSON 结构：

```json
{
  "seq": 8,
  "kind": "turn_started",
  "sessionId": "session-1",
  "requestId": "request-1",
  "source": "terminal",
  "text": "请检查当前修改",
  "sessionStatus": "",
  "turnStatus": "running",
  "error": null
}
```

精确语义如下：

- `turn_started.text` 是 A3 `normalizeInput` 后、实际交给 Worker 的本轮输入正文；
- `source` 为 `terminal` 或 `mobile` 时均使用相同语义，避免平台按来源猜测字段含义；
- 正文必须非空，UTF-8 不超过现有 `MaxPromptBytes`；
- `text_delta.text` 仍只表示 Claude 输出增量；其他 event kind 的 `text` 保持空字符串；
- envelope 与嵌套 event 的 `sessionId/requestId/seq` 关联规则不变。

这是版本 1 的结构兼容语义补充：旧客户端已把 `turn_started.text` 解码为字符串但忽略正文；新客户端利用该值展示输入。新客户端会要求 `turn_started.text` 非空，因此旧服务端与新客户端不是行为兼容组合；A5.1 必须协调更新 Service 和 Mobile Web，并通过同一门禁后才能进入 A6。里程碑 A 尚未发布，不为这一语义补充新增协议版本。

### 4.2 snapshot 边界

`TurnSnapshot` 不增加 prompt/input 字段。新连接只看到 snapshot 中现有的来源、状态和 Claude 累计输出；即使 snapshot 对应正在运行或最近完成的 PC Turn，也不恢复输入正文。

因此：

- 连接建立后的下一条 PC 输入可以实时显示；
- PC 已提交后才连接、页面刷新或显式重连，输入正文不会出现；
- 该差异是已确认范围，不属于数据丢失或协议错误。

## 5. 服务端数据流

```text
终端行输入
  → normalizeInput（trim + 大小校验）
  → Controller FIFO
  → startNext
  → turn_started{text: normalizedInput}
  → Channel 原子订阅
  → Transport event envelope
  → 已连接客户端
```

A3 `Controller` 是正文的唯一可信来源。CLI、Channel 和 Transport 不重新读取终端、不缓存第二份 prompt，也不根据 `source` 重构文本。

Session 启动前提交的首条终端输入，在获得真实 `sessionId` 后补发 `turn_started` 时同样携带 `state.current.Input.Text`。排队输入只有真正成为当前 Turn、发布 `turn_started` 后才对手机可见；手机不提前观察队列正文。

来自不同手机连接的命令都由 Channel 强制标记为 `source=mobile`，进入同一个 Controller FIFO。A5.1 不增加设备 ID、发送方身份、优先级或抢占协议；当前 Turn 运行时收到的新输入沿用 A3 现有行为排队，待前一 Turn 结算后逐条交给 Claude。审批、取消或真正中断当前 Turn 仍属于 B2，不在 A5.1 借“干预”名义提前实现。

### 5.1 多手机并发语义

Pairing 只负责证明连接持有当前 Session 的有效凭证。通过认证并订阅同一 Channel 的手机连接地位相同：

- 任意连接都可独立发送 `send_text`，无需获得控制权或等待其他手机退出；
- 每个连接只维护自己的 WebSocket 状态、`commandId` 单飞和 `command_result`，不共享客户端锁；
- Channel 把所有合法命令转交同一个 Controller，Controller 是唯一跨终端/多手机的串行化点；
- 多个连接近乎同时提交时，不承诺按设备、网络到达时间或客户端时钟排序，只以 Controller 实际接受顺序形成 FIFO；
- 每条已接受输入获得全局唯一 `requestId`，随后 `turn_started` 和 Claude 事件广播给所有订阅连接；
- 发出命令的连接仍看到自己的 `command_result`，其他连接不需要观察或关联该 `commandId`；
- 单个连接断开、变慢或输出队列溢出只影响该连接，不影响其他手机或 PC Session。

这里不消除服务端并发控制：Transport 和 Channel 可以并发接收不同连接的命令，但不得并发写 SDK Client。现有 Controller Actor/FIFO 正是唯一需要保留的竞态收敛边界。

## 6. 有界传输与大消息

现有合法输入上限为 1 MiB UTF-8，而 A4 普通 outbox 总字节上限也是 1 MiB、提前事件缓存为 256 KiB。把完整输入放入 event 后，JSON envelope 开销会使最大合法输入必然超过原有上限；如果不调整，连接会被误判为慢客户端并关闭。

A5.1 将普通 outbox 和提前事件缓存的字节上限统一提高到 2 MiB，数量上限仍保持 64 和 32：

- 单个最大合法 prompt 加 JSON envelope 可以完整入队；
- 队列仍受数量和总字节双重约束，不变成无界内存；
- 多个大事件仍会触发现有溢出关闭策略；
- 连接关闭只影响该订阅，不阻塞 Session Controller 或其他客户端。

测试必须使用接近 1 MiB 的终端输入事件证明不误关闭，并保留现有数量/字节溢出测试。若实测 2 MiB 无法覆盖最大序列化结果，应以 `MaxPromptBytes + 64 KiB` 的明确单消息预算计算常量，而不是继续扩大为无界值。

## 7. Mobile Web 归并与展示

### 7.1 输入消息模型

现有仅表示手机正文的消息类型扩展为通用输入消息，至少包含：

```ts
interface InputMessage {
  kind: 'input'
  source: 'terminal' | 'mobile'
  requestId: string | null
  text: string
  status: 'accepted' | 'unknown' | null
}
```

- `terminal` 输入由 `turn_started` 创建，`requestId` 必须存在，不显示发送确认状态；
- 当前 WebSocket 发出的 `mobile` 输入仍由成功 `command_result` 创建，状态为 `accepted`；
- 其他手机连接发出的 `mobile` 输入由 `turn_started` 创建，不显示发送确认状态；
- 断线时尚未确认的手机输入保留 `requestId: null / status: unknown`；
- Claude 回复继续使用独立 `ClaudeMessage`，不得把用户输入拼进回复正文。

### 7.2 去重规则

处理 `turn_started` 时：

1. 校验严格连续 `seq`；
2. 查找同一 `requestId` 的输入消息；
3. 若同一 `requestId` 的本地 accepted 输入已存在，校验 source 和正文一致，只创建 Claude 回复，不重复正文；
4. 若输入不存在，无论来源是 `terminal` 还是其他手机连接的 `mobile`，都由 `turn_started` 创建无确认状态的输入消息，然后创建 Claude 回复；
5. 同一 `requestId` 已存在 Claude 回复时视为不可信重复事件，沿用严格 seq/协议错误策略，不合并第二份 Turn。

A4 只对发出命令的连接保证同一移动命令的 `command_result` 先于 `turn_started`；其他订阅连接只会观察 `turn_started`。因此前端不增加乱序缓存，也不识别具体手机设备，只区分“本连接已确认”与“从 Session 事件观察到”。已有输入的来源或正文与事件不匹配时不得静默改写；应终止当前连接并通过新 snapshot 重建状态。

### 7.3 界面

- PC 输入显示正文和“电脑端”标识；
- 当前页面发送的手机输入保留“已接收”或“结果未知”反馈，其他手机输入统一显示“手机端”；
- Claude 回复保留纯文本流式展示；
- 新输入和回复继续遵守“接近底部才自动滚动”的 A5 行为；
- 不增加 Markdown、头像、时间戳或视觉设计依赖。

## 8. 安全与隐私

PC 输入只发送给已通过短期 Pair Token 认证并订阅同一 `sessionId` 的连接。A5.1 不扩大认证范围，但会让已授权手机看到 PC prompt，因此必须保持：

- 输入正文不写入 Service 日志、浏览器控制台、测试快照或文档；
- 测试只使用虚构短文本和生成的大文本，不使用真实用户 prompt；
- 错误消息不拼接正文；
- 连接隔离、token 撤销和 `sessionId` 校验继续由 A4 保证。

## 9. 错误边界

- `turn_started.text` 为空、超限或字段结构错误：协议错误，关闭当前连接；
- 已存在同 request ID 输入但 source 或正文不一致：协议错误；
- 同一 `requestId` 已存在 Claude 回复后再次收到 `turn_started`：重复 Turn，协议错误；
- outbox 或提前缓存总预算溢出：沿用 A4，仅关闭当前连接；
- 页面断线：易失消息按 A5 规则处理，不持久化或自动 replay。

## 10. 测试与门禁

### 10.1 自动化

1. A3 Controller：终端和手机 `turn_started.text` 都等于规范化输入；首个 session 初始化 Turn 同样携带正文；排队输入未启动前不发布正文。
2. A4 Transport：真实 WebSocket event 保留正文、关联字段与 seq；接近 1 MiB 的合法输入不触发容量关闭；真正超出总预算仍隔离关闭。
3. TypeScript decoder/client：合法 `turn_started.text` 解码；空正文和错误关联拒绝；连接代次规则不变。
4. reducer：PC 输入先于 Claude 回复、连续多轮、本地手机输入按 request ID 去重、其他手机输入可见、错误来源/正文拒绝、重连仍不恢复正文。
5. React：PC 输入正文和来源标识可见，本地手机消息不重复，其他手机输入统一标记，滚动行为保持。

完整门禁：

```bash
go test -race -count=1 ./internal/session ./internal/channel ./internal/transport
go test -count=1 ./...
GOFLAGS=-buildvcs=false go vet ./...
GOFLAGS=-buildvcs=false go build ./...
cd apps/mobile
npm test
npm run lint
npm run build
cd ../..
git diff --check
```

### 10.2 本机浏览器闭环

1. 在页面已连接后从 PC 终端发送文本；
2. 手机页面显示完整 PC 输入和“电脑端”标识；
3. 同一 request ID 的 Claude 流式回复紧随其后；
4. 当前页面发送文本只显示一次，并继续收到回复；如有第二个订阅页面，该页面能以统一“手机端”来源观察输入；
5. 两个手机页面近乎同时发送文本，二者均获得各自 command result，PC 按 Controller 接受顺序逐条交给 Claude，所有页面观察相同 Turn 顺序；
6. 关闭或拖慢其中一个页面不影响另一页面继续发送和接收；
7. PC 与手机交替发送至少两轮，顺序和来源正确；
8. 刷新页面，确认旧 PC 输入正文不恢复；
9. 刷新后 PC 再发送新文本，确认重新开始实时同步。

结果达到门禁后写入 `docs/testing/A5.1-result.md`，再进入 A6。

## 11. 三端共用契约核对

| 契约 | A5.1 变化 | 三端可实现性 |
| --- | --- | --- |
| 通信协议 | 版本 1 结构不变，补充 `turn_started.text` 非空正文语义 | React/TypeScript、Capacitor 和 ArkTS 均可读取标准 JSON 字符串 |
| 状态模型 | Turn 开始事件暴露当前输入；所有手机共用 `mobile` 来源，snapshot 仍不含 prompt | 三端均可维护连接期输入消息并按 request ID 去重，无需设备身份模型 |
| 配对负载 | 无变化 | 不受影响 |
| 验收用例 | 增加 PC 输入实时显示、多手机并发发送、单连接隔离、手机去重和刷新边界 | Web、Capacitor、HarmonyOS 可复用相同行为断言 |

该变化不依赖 DOM、浏览器存储、Web Crypto、线程或平台路由。三端可实现性核对通过。
