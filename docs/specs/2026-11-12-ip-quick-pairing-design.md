# IP 快速配对设计

日期：2026-11-12。状态：用户已确认独立进程内 7330 方案，实施中。

## 1. 目标与范围

保留扫码、配对链接及现有配对信息导入，新增“输入 PC IP → PC 显示六位码 → 手机输入验证码 → 进入会话”。仅面向 WhaleTerm 中已启动的 Remote 服务；不自动启动服务、不创建额外会话、不开放手机查询整台 PC 会话列表。应用退出后所有服务断开，重启不恢复。

当前代码已有后台 Registry（按 sessionId 保存服务）、Current 配对查询、前端选中会话及远程标记。目录“启动远程 CLI”还可能存在尚未扫码、尚未进入列表的待配对草稿，必须纳入可选目标。

## 2. 用户流程

手机连接页按用户设计稿实现：ccBuddy 标题、IP 输入及粘贴、连接按钮、扫描二维码、体验演示；iOS 验证阶段统一输入框：粘贴旧配对 JSON 或 Fragment 时仅显示主机地址、连接时使用原配对流程；粘贴或输入 IP 时使用快速配对，输入非法内容时提示错误；扫码沿用原流程。Android 与 Harmony 待 iOS 验收后同步。默认只需 IP，可兼容 IP:端口（IPv6 使用方括号）；不扫描端口。

手机点击连接后显示连接中；请求到达 PC 后显示验证码输入页（数字键盘，保留前导零），提示“请查看 WhaleTerm 上的六位验证码”，可返回取消。

PC 弹窗显示六位码及目标：

- 当前选中会话已开启 Remote：默认绑定该会话，显示项目和标题，无需额外确认。
- 当前选中会话未开启 Remote或没有选中会话：验证码下显示可选远程会话列表，用户选择后生效；仅一个目标时默认选中。
- 列表包含待配对草稿，显示目录与“待配对新会话”，重名时补完整路径。
- 目标在弹窗建立时固定；用户切换 PC 主界面不会悄悄改变本次配对目标。列表模式允许显式修改；手机验证时以后端已确认的选择为准。
- 关闭弹窗取消本次请求。关闭目标服务使请求失效，不自动换成其他会话。

验证码正确且目标有效后返回原有完整 Pairing。手机继续认证、订阅、取得有效快照，再保存并进入会话；目录受限的新增入口继续检查 PC/cwd。PC 显示“验证码已验证”，不将凭证交付等同于会话同步成功。待配对草稿沿用已有订阅成功后加入 PC 列表的行为。

## 3. 固定入口与职责

建议固定独立端口 7330，路径 `/quick-pair/v1`，采用 WebSocket + JSON。这是草案建议值，实施前核对项目端口使用。现有会话仍从 7331 起分配端口，旧地址、二维码和会话协议不变。

第一个 Remote 成功启动后尝试启动快速入口；最后一个 Remote 关闭后关闭入口及待处理请求。入口端口被占用时明确提示 PC“快速配对不可用，仍可扫码”，不静默换端口、不撤销已启动的会话服务。启动/关闭需串行协调，避免并发服务启停误关入口。

WhaleTerm 后台负责入口、请求、验证码、有效目标列表和凭证交付；前端负责读取当前选中会话并展示弹窗，通过本机 Wails 调用选择目标。后台重新核对目标存在，不信任前端图标作为运行依据。前端未就绪或刷新时取消尚未完成的请求，手机重试；不持久化验证码。

没有 Remote 时不监听该入口，手机连接超时或被拒绝后提示：“无法连接，请先在 PC 启动远程服务，并检查手机是否能访问该 IP。”不能仅凭超时断言 PC 没有启动服务。

## 4. 最小握手契约（草案）

此入口不使用需要 sessionId 的现有会话 envelope。每条消息使用 `{version:1,type,requestId,payload}`，请求与当前连接绑定；一次连接仅处理一次配对。

| 方向 | type | 内容 |
| --- | --- | --- |
| 手机→PC | begin | 空 payload；不提交 sessionId/cwd |
| PC→手机 | ready | requestId、expiresAt；PC 弹窗准备完成后发送，不含验证码及会话列表 |
| 手机→PC | verify | 六位数字字符串 code |
| PC→手机 | paired | 当前目标的完整 Pairing v1，含会话地址、凭证和元数据 |
| 双向 | cancel | 取消请求，不关闭已有会话 |
| PC→手机 | error | 固定 code：busy、invalid_code、target_required、target_unavailable、expired、cancelled、unavailable |

同一 PC 同时处理一个配对弹窗，其他请求返回 busy，不覆盖已有请求。建议验证码有效两分钟、最多五次错误；使用随机六位数字，仅作一次配对验证，不替代原会话随机 Pair Token。验证码和凭证不写日志、URL或普通存储。不添加额外握手步骤。

手机建连/等待 PC ready 总计最多八秒；收到 ready 后进入两分钟输入窗口，不能沿用会话连接的短超时。未选目标时 verify 返回 target_required，不扣验证码错误次数；过期、取消、断线释放请求。验证成功时原子消费请求并读取目标当前有效 Pairing；发送结果后结束握手。结果丢失重新发起配对，不重复创建会话。后续认证失败保留原有配对失败处理。

手机取得会话地址时采用本次实际连接的 PC 主机地址及目标服务端口、路径，避免后台默认网卡与用户输入的可达网卡不一致；不改变原扫码地址生成规则。

## 5. 兼容与三端

既有 Pairing v1、会话消息、Session/Turn、唯一 Host/Client/FIFO、推送绑定均保持原样。新增入口只交付指定会话的现有凭证，不签发可访问全机的权限。

iOS/Android 共用 React 配对界面和连接逻辑；Harmony 用 ArkTS 实现相同 JSON、超时和错误语义。各端验证成功后接入原配对校验、安全存储、订阅和通知登记流程。二维码和导入作为旧 PC 的回退方式；旧客户端不使用新入口。浏览器保留现有内存凭证边界。

三端契约仅依赖 WebSocket、JSON、定时器和普通数据，无 DOM 或单平台字段。用户确认设计后，将共用契约核对及已确认范围写入 DECISIONS/REQUIREMENTS，再编写实施计划；本草案不视为技术方案已批准。

## 6. 实施顺序与验收

1. WhaleTerm：Registry 运行目标快照（含草稿）、固定入口生命周期、握手状态机、Wails 弹窗和选择接线。
2. 移动端：IP入口、验证码页，成功后复用原配对流程；iOS/Android 与 Harmony 同步契约。
3. 定向测试后进行 PC 与三端真机验收，不发布或自动提交。

验收覆盖：当前目标有效、其他目标选择、唯一目标、待配对草稿、无服务、端口冲突、错误/过期验证码、PC/手机取消、多手机 busy、前端刷新、目标关闭、切换 PC 会话不串线、响应丢失重试、多网卡地址、原扫码/导入回归。成功需取得快照且能完成一轮会话交互；已有会话不重建，凭证不泄露到日志。应用重启后不恢复远程服务。
