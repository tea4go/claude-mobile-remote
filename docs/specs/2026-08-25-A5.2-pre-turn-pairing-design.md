# A5.2 首轮前配对分阶段设计

- 日期：2026-08-25
- 子阶段：A5.2 首轮前配对（里程碑 A）
- 状态：已由用户书面确认
- 依据：用户确认的新会话首轮前配对需求、Claude CLI `--session-id` 能力、D28、D38

## 1. 问题与目标

当前新会话只有在 PC 提交第一条消息、Claude init 返回真实 `sessionId` 后，CLI 才注册 Channel 并输出配对信息。这迫使 PC 发起首个 Turn，手机无法在空闲的新会话中扫码后发送第一条消息。

A5.2 将流程调整为：Service 启动新会话时预先生成 UUID，并通过 Claude CLI `--session-id` 将其指定为真实 Claude session ID；恢复会话直接使用已有 ID。SDK Connect 成功后立即开放配对，PC 或任意已配对手机都可以成为第一条真实消息的来源。

成功标准：

- 新会话不发送空对话，也能在首个 Turn 前产生有效配对负载；
- 手机可以发送第一条真实消息并创建 Claude 会话；
- PC 与多个手机近乎同时发送时继续使用现有 Controller FIFO；
- Claude init 确认的 ID 必须与预期一致；
- 版本 1 配对负载、WebSocket envelope 和三端状态结构保持不变。

## 2. 范围

### 2.1 A5.2 实现

- `claude-agent-sdk-go` 增加 `WithSessionID(uuid)` 并映射 Claude CLI `--session-id`；
- SDK 明确校验 `WithSessionID` 与 `WithResume` 互斥；
- 新会话在创建 Host 前生成 UUID，恢复会话在创建 Host 前取得已有 ID；
- Host 从 Connect 前持有预期 ID，首个 init/Result 必须校验一致；
- Controller 区分 `sessionId` 已预留和 Claude init 已确认；
- Remote 在 Controller/SDK Connect 成功后、首个 Turn 前注册 Channel 并签发凭证；
- 保持 `session_started → turn_started → text_delta` 的首轮事件顺序；
- 自动化和真实 SDK 门禁覆盖新建、恢复、手机首条、并发、失败清理和兼容性。

### 2.2 A5.2 不实现

- 本地 `channelId`、临时 session ID 或动态 Channel 重命名；
- 通过空 prompt、隐藏 system prompt 或无业务意义 Query 初始化 Claude；
- 多会话选择器、历史列表或跨进程 Session Registry；
- 修改版本 1 envelope、配对负载或 snapshot JSON 结构；
- 自动重连、事件 replay、取消、审批或设备主从关系；
- A6 VPN 真机网络联调。

## 3. 方案与替代方案

### 3.1 采用方案：预分配真实 Claude session ID

本机 Claude Code 2.1.179 的 CLI 明确支持：

```text
--session-id <uuid>  Use a specific session ID for the conversation
```

Service 使用安全随机 UUID v4 作为新会话 ID，并把它传给 Claude CLI。该 ID不是只存在于应用内的替代身份；当第一条真实 Query 启动时，Claude 必须以同一个 ID创建和持久化会话。

`--session-id` 只指定身份，不携带 prompt。SDK `Connect` 不调用 `Query`，因此 A5.2 不引入空 Turn、Claude 回复、上下文污染或人为初始化消息。该无副作用假设必须由真实 SDK 门禁验证，验证通过前不进入 Service 集成。

### 3.2 未采用：本地 Channel ID 延迟绑定

该方案会先生成应用内部 `channelId`，首轮后再绑定 Claude `sessionId`。它能解耦路由与 Claude 身份，但需要修改配对负载、envelope、snapshot、Channel Registry 和三端客户端，并处理动态绑定与重连语义。当前单会话目标不需要这层复杂度。

### 3.3 未采用：隐藏初始化 Query

自动发送空白或无业务意义消息会产生真实 Turn，可能污染上下文、历史、费用和权限流程，也让用户的第一条消息失去“首轮”语义，因此禁止采用。

## 4. Session 身份模型

每个 Controller 从创建起持有不可变的 `sessionId`，并额外维护仅限 PC 内部的确认状态：

```text
reserved    Service 已确定真实 ID，配对与路由可用
confirmed   Claude init 已返回相同 ID，Session 已开始
```

这不是两个 Session ID。配对负载、Channel、snapshot、事件和命令始终使用同一个真实 ID；`confirmed` 不进入版本 1 JSON。

内部不变量：

- `sessionId` 在 Host/Controller 创建前确定，生命周期内不可修改；
- 新建模式只能配置 `WithSessionID`，恢复模式只能配置 `WithResume`；
- Connect 成功但尚无 Query 时，Session=`starting`、Turn=`idle`、confirmed=false；
- confirmed=false 时允许认证、订阅和 Submit；
- 首个 init 或 Result 的非空 ID必须等于预期 ID；
- 每个 Session 最多发布一次 `session_started`；
- `turn_started` 不得早于 `session_started`；
- ID 不一致时不得把 Channel 动态迁移到 Claude 返回的新 ID。

## 5. 新建与恢复生命周期

### 5.1 新会话

```text
Service 生成 UUID
  → NewHost(WithSessionID(uuid))
  → Controller 以 uuid / confirmed=false 创建
  → SDK Connect(--session-id uuid)
  → Remote 注册 Channel(uuid) 并签发 Pair Token
  → PC/手机提交第一条真实消息
  → Controller 接受并启动唯一 Worker
  → SDK Query
  → Claude init 返回 uuid
  → Host 校验一致
  → Controller confirmed=true
  → session_started
  → turn_started
  → Claude 增量与 Turn 终态
```

首条 Query 前退出时，Service 只撤销凭证和关闭进程；没有业务 Turn，不应产生可恢复对话内容。未使用的随机 UUID自然作废。

### 5.2 恢复会话

```text
Service 取得已有 sessionId
  → NewHost(WithResume(sessionId))
  → Controller 以该 ID / confirmed=false 创建
  → SDK Connect(--resume sessionId)
  → 立即开放同一 ID的配对
  → PC/手机提交第一条恢复消息
  → Claude init/Result 返回相同 ID并确认
```

恢复失败时不能静默接受 Claude 新建的其他 ID。返回值不一致按 Session 级错误处理。

## 6. Controller 与事件顺序

Controller 继续是终端和所有手机输入的唯一串行化点，不改变 Actor、FIFO、Worker 或 request ID 模型。

当前实现用 `snapshot.SessionID != ""` 近似判断 Session 是否初始化。A5.2 后该条件不再成立，必须改为独立的 confirmed 状态：

- session ID 已预留但未确认时，Submit 正常生成 request ID并进入 FIFO；
- 第一条输入成为 current 并交给 Worker，但 `turn_started` 暂缓；
- init 确认后先发布 `session_started`，再发布 current 对应的 `turn_started`；
- init 前收到的 Claude 文本继续沿用现有缓冲规则，在 Turn 开始后释放；
- 后续排队输入只在前一 Turn 结算后启动。

首轮事件顺序保持：

```text
command_result（仅发送连接）
session_started（所有订阅端）
turn_started（所有订阅端）
text_delta...
turn_completed / turn_failed
```

其他订阅端不接收发送连接的 `command_result`，仍从 `session_started/turn_started` 观察首轮。

## 7. 多入口并发

配对完成后，PC 和多个手机都可提交第一条消息。该场景不增加特殊锁或选主：

- Transport 可并发接收不同手机的命令；
- Channel 继续把手机来源强制为 `mobile`；
- Controller 按实际接受顺序生成全局 request ID和 FIFO；
- 第一条被接受的输入触发首个 Query；
- 其余输入排队，在 Claude 确认 Session 并完成前一 Turn 后依次执行；
- 不承诺设备优先级、网络到达时间或客户端时钟顺序；
- 单连接的 command result、顺序门和慢连接隔离保持 A4/A5.1 语义。

该并发虽然少见，但必须自动化覆盖，防止首轮初始化绕过现有唯一 Worker 边界。

## 8. Remote 与配对时机

Remote 激活从 `session_started` 事件分支前移到 Controller/SDK Connect 成功之后：

1. Controller Start 成功；
2. Transport Start 成功；
3. 使用预期 ID注册 Channel；
4. Pairing Manager 为精确 ID签发凭证；
5. CLI 输出配对负载；
6. 事件循环开始处理 PC、手机和 Claude 事件。

`session_started` 不再调用 `remote.Activate`，只更新 Session 状态和输出可见确认，避免重复注册 Channel 或重复签发凭证。

Pair Token 的随机性、TTL、轮换、撤销和日志保密规则不变。首轮前 token 过期时只为同一预期 ID轮换凭证。

## 9. 共用协议与手机行为

A5.2 不改变版本 1 wire shape。首轮前订阅返回的 snapshot 示例：

```json
{
  "sessionId": "73f9c6c8-79d6-49a0-9b44-5d73e26ee284",
  "sessionStatus": "starting",
  "sessionError": null,
  "seq": 0,
  "turn": {
    "status": "idle",
    "requestId": "",
    "source": "",
    "message": "",
    "error": null,
    "pendingAction": null
  },
  "queueDepth": 0
}
```

现有 Mobile Web 已允许 Session=`starting` 且没有 pending command 时发送文本，因此正常实现不需要新增状态枚举、页面或命令类型。页面可以沿用当前“正在启动/等待开始”状态；首条命令接受只表示进入 Controller，不表示 Claude init 已完成。

## 10. SDK 能力门禁

Service 集成前必须先在 `claude-agent-sdk-go` 完成独立门禁：

- Options 增加可选 Session ID；
- `WithSessionID` 只接受合法非空 UUID；
- CLI discovery 构造 `--session-id <uuid>`；
- Session ID 与 Resume 同时配置时在启动子进程前失败；
- 单元测试覆盖参数、省略、非法值和互斥；
- 真实 Claude 验证 Connect 后尚无业务 Turn；
- 第一条真实 Query 的 init 和 Result 返回预设 ID；
- Query 前关闭不产生业务对话内容；
- Resume 路径继续使用已有 ID，且不传 `--session-id`。

若真实门禁发现 Connect 会产生业务副作用、CLI 忽略指定 ID或无法稳定回传相同 ID，立即停止 A5.2 Service 集成并回到设计评审，不用隐藏 Query规避。

## 11. 错误与清理

| 场景 | 行为 |
| --- | --- |
| UUID 生成失败 | Service 启动失败，不创建 Host、不启动配对 |
| 新建/恢复选项冲突 | SDK 配置失败，不启动 Claude 子进程 |
| Claude CLI 不支持 `--session-id` | Connect 返回兼容性错误，不显示配对信息 |
| SDK Connect 失败 | Service 启动失败，不注册 Channel、不签发 token |
| Transport 启动失败 | 关闭 Controller/SDK，不留下半启动 Service |
| Channel 注册或 token 签发失败 | 撤销已创建资源并关闭 Controller/SDK |
| 首个 init/Result ID为空或不一致 | Session=`failed`，清空队列，撤销凭证并关闭已认证连接 |
| 首条 Query 前退出 | 撤销 token、关闭连接和 SDK；无业务 Turn |
| 首轮执行失败但 Session scope 可恢复 | 沿用现有 Turn failure 规则；ID 已确认时 Session 可继续 |
| Resume 实际返回新 ID | Session failure；禁止静默切换或 Channel 迁移 |

错误信息不得包含 Pair Token、完整配对负载、prompt、Claude 配置或原始敏感输出。

## 12. 测试与验收

### 12.1 自动化

1. SDK Options/CLI：合法 UUID、非法 UUID、SessionID/Resume 互斥、命令参数快照。
2. Host：预期 ID首轮确认、Result fallback 确认、空/变化/不一致 ID失败、最多一次 session started。
3. Controller：预置 ID但未确认时可 Submit；事件仍是 session started 后 turn started；并发首条只启动一个 Worker；队列保持 FIFO。
4. CLI/Remote：无终端输入时 Connect 后立即输出配对；session started 不重复 Activate；启动失败逆序清理。
5. WebSocket：首轮前认证、订阅 starting/idle snapshot、手机首条 command result、随后完整事件流。
6. 多手机：PC 与两个手机并发提交，全部接受并按 Controller 顺序执行，没有 SDK 并发写。
7. 失败隔离：ID不一致撤销 token、关闭连接、拒绝队列；首轮前退出无 Query。
8. 回归：A5.1 输入同步、command result 顺序门、token 轮换、刷新重连和慢连接隔离全部通过。

### 12.2 真实 SDK 门禁

使用虚构短 prompt 和新随机 UUID验证：

1. `Connect(--session-id UUID)` 成功；
2. Connect 后不出现业务 Turn；
3. 首个 Query 的 init/Result ID等于 UUID；
4. 第二轮沿用同一 ID和上下文；
5. Query 前关闭不留下包含业务消息的 transcript；
6. 已有 Session 的 Resume 返回请求的 ID。

真实验证不得把用户会话内容、凭证或 Claude 配置写入仓库。

### 12.3 浏览器人工闭环

1. 启动 PC Service，不在终端输入消息；
2. 立即取得二维码或配对负载；
3. 手机连接后看到 waiting/starting 状态；
4. 手机发送第一条消息；
5. PC 和所有订阅页面看到该手机输入及 Claude 回复；
6. PC 再发送一轮，确认同一 Session 连续工作；
7. 两个页面近乎同时提交，确认均被接受且按统一 Turn 顺序执行；
8. 退出并使用同一 ID Resume，确认首轮前仍可配对且上下文延续。

达到门禁后写入 `docs/testing/A5.2-result.md`，再进入 A6。

## 13. 三端共用契约核对

| 契约 | A5.2 变化 | 三端可实现性 |
| --- | --- | --- |
| 通信协议 | 版本 1 envelope 和 event 不变 | React、Capacitor、ArkTS 无需新增解析分支 |
| 状态模型 | 首轮前即可看到非空 sessionId、starting/idle snapshot | 三端已有状态均可表达，并可在 starting 时发送文本 |
| 配对负载 | JSON 结构不变，签发时机提前 | 三端仍按同一 sessionId/token 认证 |
| 验收用例 | 增加首轮前扫码、手机首条、并发首条和 Resume 首轮前配对 | 不依赖浏览器特有 API，三端可复用 |

Service 生成的 UUID已通过 `--session-id` 交给 Claude，不是 Web 专属或应用内部路由 ID。三端可实现性核对通过。
